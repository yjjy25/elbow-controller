# RED_Demo 项目接手说明

> 2026-11-03 更新：已新增视觉区域控制电机，USART3 改为 115200，上电 PWM 为 0。下文为改动前的接手记录；当前行为、接线和验证结果见 [视觉联动说明](视觉联动说明.md)。

梳理日期：2026-11-03。依据当前源文件和 Keil 工程配置整理；引脚是软件配置，尚未对照外部原理图逐线核验，也没有做上板验证。本文不修改运行代码。

## 1. 先看懂它现在做什么

这是一个 STM32F407VETx 的裸机工程，使用 STM32 HAL 库和 Keil ARMCC5。当前应用是“视觉与底盘 CAN 协同作业 + 四路区域电机控制 + 编码器测速 + OLED/串口状态输出”。

- 四路电机 A/B/C/D：方向引脚被设置为固定组合，PWM 都是约 50%。
- 四路编码器：硬件定时器持续计数，每 10 ms 计算一次转速。
- OLED：每约 100 ms 更新四路 RPM 和 CAN 自检结果。
- USART3：9600、8N1，每约 500 ms 输出一行状态。
- CAN2 使用正常模式、1 Mbit/s，与底盘 CAN3 交换作业状态，每 100 ms 上报。
- LED：PB2 每 500 ms 翻转一次，完整亮灭周期约 1 秒。

虽然目录叫“肘击装置”，但当前业务代码中没有完整肘击动作序列、目标角度控制、PID 调速或串口控制协议。不能仅根据目录名推断已实现这些功能。

## 2. 目录应该怎么看

```text

├─ RED_Demo.ioc                   ← CubeMX 外设配置，可用 CubeMX 打开
├─ Core/
│  ├─ Inc/                        ← 外设声明、引脚命名、HAL 配置
│  └─ Src/
│     ├─ main.c                   ← 程序入口、初始化顺序、主循环
│     ├─ tim.c                    ← PWM、编码器、采样定时器配置
│     ├─ gpio.c                   ← 普通 GPIO 模式与初始电平
│     ├─ usart.c                  ← USART3 波特率、引脚、中断配置
│     ├─ can.c                    ← CAN2 时序、工作模式、引脚配置
│     ├─ stm32f4xx_it.c            ← 中断入口，转交 HAL 处理
│     ├─ stm32f4xx_hal_msp.c       ← HAL 底层公共初始化
│     └─ system_stm32f4xx.c        ← 芯片基础系统初始化
├─ BSP/                          ← 最需要读的应用代码
│  ├─ fun.c / fun.h               ← 电机、测速、显示、串口集中在这里
│  ├─ can_test.c / can_test.h     ← CAN 作业收发和诊断统计
│  ├─ headfile.h                  ← 把常用头文件集中包含
│  └─ OLED/
│     ├─ OLED.c / OLED.h         ← 软件 I²C、显存、字符/图形绘制

└─ MDK-ARM/
   ├─ RED_Demo.uvprojx           ← Keil 工程入口
   ├─ startup_stm32f407xx.s      ← 中断向量表与复位启动
   ├─ .vscode/                  ← 编辑器配置与构建日志
   └─ RED_Demo/                 ← .axf/.o/.map 等构建输出
```

`.c` 通常放实现，`.h` 放函数声明、类型和宏。例如主循环通过 `fun.h` 知道 `OLED_Display()` 的声明，真正实现位于 `fun.c`。

Drivers 里文件多，不等于都在运行。Keil 的 `uvprojx` 决定哪些源码参与编译。当前应用没有使用 RTOS；CMSIS 目录中带有 RTOS/DSP 文件也不能说明应用用了这些组件。

外层还有 `RED_Demo.rar` 和 `原理图.pdf`。RAR 是压缩包，不会参与当前工程编译；原理图用于核对硬件，不能替代源码中的实际配置。

## 3. 上电后怎么走

```text
复位 → startup_stm32f407xx.s 的 Reset_Handler
     → SystemInit → C 运行库 __main → main()
     → HAL_Init()
     → SystemClock_Config()：HSI + PLL，系统时钟 80 MHz
     → MX_GPIO / MX_TIMx / MX_CAN2 / MX_USART3 初始化
     → Init()：启动 OLED、串口接收、PWM、编码器、TIM5
     → CAN_Test_Init()：配置接收过滤器并启动 CAN2
     → while (1)：不断调用显示、LED、方向设置、CAN 自检、串口上报
```

`MX_xxx_Init()` 主要是“配置外设”；`Init()` 里多处 `HAL_xxx_Start()` 才让外设开始工作。例如只配置 TIM1，并不等于 PWM 已经输出。

主循环的核心相当于：

```c
while (1) {
    OLED_Display();
    LED_Blink(500);
    Motor_Statu(1);  // 设置 A 路方向引脚
    Motor_Statu(2);  // B 路
    Motor_Statu(3);  // C 路
    Motor_Statu(4);  // D 路
    CAN_Test_Task();
    UART_SendStatus();
}
```

这些函数每轮都会被调用，但函数内部通过 `HAL_GetTick()` 判断是否到时间，所以显示和发送并非每轮都执行。这里的时间间隔是主循环轮询实现的，会受到主循环中其他耗时操作影响。

## 4. 电机与定时器对应关系

| 电机 | 数组下标 | PWM 输出 | 方向引脚 IN1 / IN2 | 编码器定时器 | 编码器 CH1 / CH2 引脚 |
|---|---|---|---|---|---|
| A | 0 | TIM1_CH1 / PE9 | PC0 / PC1 | TIM8 | PC6 / PC7 |
| B | 1 | TIM1_CH2 / PE11 | PC2 / PC3 | TIM3 | PB4 / PA7 |
| C | 2 | TIM1_CH3 / PE13 | PC4 / PC5 | TIM4 | PD12 / PD13 |
| D | 3 | TIM1_CH4 / PE14 | PD3 / PD5 | TIM2 | PA0 / PA1 |

`Motor_Statu(1)` 中的 `1` 表示电机编号 A，不表示“正转模式 1”。四次调用分别设置四路，不是让同一台电机切换四种状态。

当前四路都写 IN1=低、IN2=高。机械上到底正转还是反转，取决于驱动器、电机接线和安装方向。

### PWM 如何决定输出

`tim.c` 配置 TIM1 的 PSC=79、ARR=99，`fun.c` 的 `Init()` 又设置 ARR=99、CCR1~4=50。按当前 80 MHz 定时器时钟：

```text
PWM 频率 = 80,000,000 / (79+1) / (99+1) = 10,000 Hz
占空比   = 50 / (99+1) = 50%
```

CCR 是比较寄存器，决定 PWM 高电平所占比例。当前没有根据 `Speed[]` 修改 CCR，因此是固定占空比开环运行。“50%”不是“50 RPM”，也不代表额定转速的一半。

## 5. 转速为什么不在 while 里算

测速由 TIM5 的周期中断触发：

```text
编码器脉冲 → TIM8/3/4/2 硬件计数
TIM5 每 10 ms 触发中断
  → stm32f4xx_it.c：TIM5_IRQHandler()
  → HAL_TIM_IRQHandler(&htim5)
  → fun.c：HAL_TIM_PeriodElapsedCallback()
  → 保存计数差到 Encoder_Count[]，计算 RPM 到 Speed[]
主循环读取 Speed[] → OLED / 串口
```

硬件负责数脉冲，CPU 每 10 ms 读取一次，因此不需要每个编码器脉冲都进入中断。编码器启动使用 `HAL_TIM_Encoder_Start()`，不是 `_Start_IT()`。

TIM5 的 PSC=79、ARR=9999：`80 MHz / 80 / 10000 = 100 Hz`，即 10 ms 一次。

`fun.c` 中当前采用的换算是：

```c
Encoder_CountsPerRev[4] = {384, 384, 384, 384};
Speed[i] = delta * 6000 / Encoder_CountsPerRev[i];
```

`delta` 是这 10 ms 内的计数差；6000 来自每秒 100 次采样乘每分钟 60 秒。例如差值 64，按每圈 384 计数，结果是 1000 RPM。

接手时必须确认 384 的定义：它应当是所测轴每圈的有效计数，需考虑编码器四倍频和减速比。否则显示数值会按比例偏差。当前整数计算会截断小数，每个采样计数约对应 15.625 RPM，低速时读数可能跳动。

TIM8/3/4 使用 16 位计数范围，TIM2 使用 32 位；代码通过相邻计数差处理回绕。每次采样间的计数变化应小于对应计数范围的一半。`Encoder_Count[]` 是单个采样窗口的增量，不是累计圈数或累计位置。

`volatile` 表示这些变量可能被中断修改；它本身不保证多变量快照一致。显示和串口代码用短暂关闭中断的方式复制四路转速，再恢复原来的中断状态。

## 6. CAN 协同作业

`Core/Src/can.c` 配置 CAN2，`BSP/can_test.c` 负责业务收发，`BSP/work_control.c` 负责作业状态机。

- 正常模式，`40 MHz / 5 / (1+5+2) = 1 Mbit/s`。
- PB12=CAN2_RX，PB13=CAN2_TX。通过外部收发器连接 CANH、CANL 和参考地。
- 过滤器组 14 仅接收标准数据帧 0x611，向底盘发送 0x610，载荷 8 字节。
- 上电握手后执行 SLOW、WAIT、STOPPED、逐次肘击、复检、GO、GO_ACK 和离树重置。
- 两端每 100 ms 发送状态，配对后失联 500 ms 进入故障停车。
- 参数集中在 `BSP/vision_motor.h`，协议定义在 `BSP/work_can_protocol.h`。

保留 `CAN_Test_*` 统计变量名称用于原显示和工程调用。状态 0 表示等待，1 表示对端在线，2 表示初始化错误，3 表示发送错误，4 表示接收错误，5 表示对端超时。任务故障以 `Vision_WorkState` 和 `Vision_WorkResult` 为准。

联合离线验证运行 `tests/verify_work_can.py`，串口和动作回归运行 `tests/verify_vision_motor.py`。真实总线、机构返回位置和车辆停车效果需要实机联调。

## 7. OLED 和串口

### OLED

软件通过 GPIO 模拟 I²C，没有配置硬件 I²C 外设。PA2=SDA、PA3=SCL，开漏输出；代码发送的写地址字节 `0x78` 对应七位地址 `0x3C`。显存为 `8 × 128` 字节，对应 128×64 单色画面。

显示顺序是 `OLED_Clear()` 清软件显存、`OLED_ShowString()` 向显存写字、`OLED_Update()` 把显存送到屏幕。只调用 ShowString 不会立即刷新硬件。

当前画面上方四行显示 A~D RPM，下方四行显示 CAN 状态、TX、RX、ERR 和 S。刷新失败会清除 `OLED_Ready`，后续每约 1 秒尝试重新初始化。

注意 `OLED_Init()` 含 `HAL_Delay(100)`，软件 I²C 传输本身也占用主循环时间。因此 OLED 尤其重试初始化时会拖延主循环里的 CAN/串口任务；TIM5 测速中断仍可运行，但不代表整个程序都是无阻塞执行。

### USART3

PB10=TX、PB11=RX，9600 bit/s、8 数据位、无校验、1 停止位。主循环约每 500 ms 使用 `HAL_UART_Transmit_IT()` 发状态，正在发送时跳过，使用静态缓冲区保证中断发送期间数据有效。

输出格式示意（数值仅为示例）：

```text
A:1000 RPM B:1000 RPM C:1000 RPM D:1000 RPM | CAN2 WORK OK TX:10 RX:10 ERR:0 S:1
```

接收使用 `HAL_UARTEx_ReceiveToIdle_IT()`：空闲或缓冲区满时进入回调，设置 `uart_flag`、记录 `uart_rx_size`，然后重新开启接收。它使用中断，不是 DMA。

目前没有后续代码消费这个接收标志，也没有命令解析器。收到字符串并不会改变电机。缓冲区长度为 32，数据不保证以 `\0` 结尾，重新接收还会复用缓冲区；以后加协议需要先复制有效数据或设计队列。

## 9. 将来改需求，去哪里改

| 想做什么 | 主要入口 | 需要同时考虑 |
|---|---|---|
| 改固定 PWM | `fun.c` 的 Init()，以及 `tim.c` 初始 Pulse | 两处都有当前值；CCR 不是 RPM |
| 加正反转、停止 | `fun.c` 的 Motor_Statu() | 当前主循环会反复写方向；驱动器制动/滑行语义要查硬件 |
| 修正测速比例 | `Encoder_CountsPerRev[]` | 编码器计数、减速比、所测轴 |
| 加恒速控制 | 新增目标速度与控制逻辑，再调整 CCR | 当前只有测速，无 PID/输出限幅/启动停止策略 |
| 用串口控制 | 接收回调之后增加数据交接和解析 | 当前只有状态上报，不能直接把接收缓冲当字符串 |
| 连外部 CAN 设备 | `can.c` 工作模式和 `can_test.c` 应用逻辑 | 需要匹配外部协议、ID、波特率，并检查收发器与总线 |
| 改屏幕内容 | `OLED_Display()` | 字符先写显存，再 Update；屏幕高度为 64 像素 |
| 改引脚/外设频率 | `.ioc`、对应 Core 初始化文件 | CubeMX 重新生成可能覆盖手写代码 |

## 10. 接手时应当记住的边界

1. 上电初始化会启动四路 PWM，主循环随即设置固定方向；具备驱动供电和接线条件时，电机可能直接转动。当前源码没有单独的用户启动命令或急停输入逻辑。
2. 编译通过只证明构建成功，不能确认机械转向、转速比例、OLED 接线和外部 CAN 通信。
3. `headfile.h` 集中包含头文件，而 `fun.h` 又反向包含它，存在循环依赖；包含保护让它目前能工作，但后续拆模块时应减少这种相互依赖。重复 include 通常不会重复执行代码。
4. `fun.c` 混合了电机、测速、显示、串口多个职责。理解时可按本文分块，后续有实际修改需求时再考虑拆文件。
5. CubeMX 的 `USER CODE BEGIN/END` 用于保留手写代码。当前 `main.c` 的 `headfile.h` 位于 Header 用户区开始标记之外；重新生成前应备份并检查差异，不能假设所有手写内容都会保留。
6. 中文注释存在编码显示问题；阅读乱码时先确认编辑器编码，不要批量转码再覆盖整个工程。

接手后的第一轮硬件核对，建议记录四件事：每路电机对应哪个机构、方向定义、所测轴每圈计数、驱动器的停止方式。这些信息决定以后控制代码里的数值是否有实际意义。
